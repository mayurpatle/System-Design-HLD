1. Head-of-line blocking, finally solved at the right layer. HTTP/2 multiplexes streams over one TCP connection, so a single lost packet stalls every stream — TCP must deliver bytes in order and doesn't know your streams exist. QUIC makes streams a transport-level primitive: they share one connection (one handshake, shared congestion state) but are delivered independently, so loss on one stream mostly doesn't block the others. This is the answer to "why HTTP/3?"
2. 1-RTT handshake by merging transport and crypto. QUIC folds TCP's three-way handshake into the TLS 1.3 handshake — it keeps TLS handshake messages but replaces the TLS record layer with its own framing. Result: one round trip instead of two. Encrypted-by-default is a design goal, not an add-on.
3. Connection IDs and connection migration. TCP identifies a connection by the 4-tuple, so a NAT rebinding or a phone switching WiFi↔cellular kills it. QUIC adds an opaque connection ID, so the connection survives an IP/port change. The catch worth mentioning: anycast + ECMP routers route by 4-tuple, so packets for one connection can land on different servers — the fix is smarter L4 load balancing in software (the post cites Facebook's Katran).
4. QPACK vs HPACK. HPACK's dynamic table works because TCP guarantees order. QUIC has no ordering across streams, so request B can arrive before request A and reference a header the decoder hasn't seen. gQUIC's fix — serialize all headers onto one stream — reintroduced the HOL blocking QUIC exists to remove. QPACK instead uses two extra unidirectional streams (table updates + acknowledgements), and the encoder may only reference a dynamic entry after it's been acknowledged. Nice generalizable lesson: removing ordering guarantees breaks every mechanism that silently assumed them.
5. Reflection/amplification defense. UDP is spoofable and QUIC's handshake is asymmetric (tiny ClientHello, huge certificate chain). Two mitigations: pad the client's initial packet to a minimum size, and the Retry packet — the server returns a small cryptographic token the client must echo, proving it owns its source IP. Cost: the handshake goes back to 2 RTT, which is why smaller certs (ECDSA, cert compression) matter.
6. Ossification and user-space deployment. Middleboxes make wrong assumptions and freeze protocols (this is why TLS 1.3 took years). Encrypting metadata — even packet numbers — is an anti-ossification measure. And running over UDP puts QUIC in user space, so browsers ship protocol changes without waiting for OS kernel updates. Great answer to "how do you evolve a protocol that's deployed everywhere?"
7. The honest cost. Decades of TCP offload work in NICs and kernels doesn't exist for UDP yet — hence UDP GSO and zero-copy sockets on Linux. Worth citing: new protocol ≠ automatically faster until the ecosystem catches up.

Real-world use cases
Mobile apps — connection migration is the killer feature: walking out of a coffee shop no longer drops your uploads or video stream.
Lossy/high-latency networks — congested WiFi, cellular, emerging markets. Independent stream delivery plus the 1-RTT handshake is where the measured wins are biggest.
CDN edges — Cloudflare, Google, Meta serve HTTP/3 by default now; if you serve users on mobile, enabling HTTP/3 at your CDN is a config change with real gains.
gRPC and internal RPC — gRPC over HTTP/3 gets the same per-stream isolation, which matters for many concurrent RPCs on one connection.
Anycast/L4 load balancing design — if you ever build or debug edge routing, connection-ID-aware balancing (Katran-style) is the concrete architectural implication.
Anything you design with multiplexing — the QPACK story transfers directly: if you multiplex independent work over a shared channel, any shared mutable state (compression tables, sequence assumptions) needs explicit synchronization.

The one-liner to have ready: HTTP/2 removed head-of-line blocking from HTTP but left it in TCP; QUIC removes it from the transport by making streams first-class over UDP, and folds the crypto handshake in to save a round trip.
