# BM25: The Next Generation of Lucene Relevance — Study Notes

**Source:** Doug Turnbull, **OpenSource Connections**, 16 October 2015
https://opensourceconnections.com/blog/2015/10/16/bm25-the-next-generation-of-lucene-relevation/

> **Attribution note:** this one isn't on Elastic's blog — it's an OpenSource Connections (o19s) post. Elastic and others linked to it heavily when the switch landed, which is probably why it gets filed under "Elastic blog." The other canonical piece on the same topic *is* Elastic's: Shane Connelly's *Practical BM25* series.

**Context:** Written when Lucene had just switched its default similarity to BM25 in trunk, meaning a new default scoring formula was coming to Solr 6 and Elasticsearch. The article's job is practical, not theoretical: what was classic TF*IDF, what does BM25 do better, how do you tune it, and is it right for everything?

**Where this sits in the stack:** BM25 and TF*IDF both occupy the same slot — what Lucene calls the **field weight**, which measures how much matched text is *about* a search term. Swapping similarities swaps that component; the rest of the query machinery is unchanged.

---

## 1. Classic Lucene similarity — the intuition

TF*IDF is described as a rough approximation of how users value a text match, built on two factors that track human judgment:

- **Term frequency (tf)** — how often does "dog" appear in this document? 3 times? 10?
- **Inverse document frequency (idf)** — document frequency counts how many docs contain the term; its inverse measures how *special* the term is. Rare term (one doc) vs. common term (nearly all docs).

Together they measure the **relative concentration** of a term. "dog" common here but rare elsewhere → high score, this doc is about dogs. "dog" appears once here but prominently everywhere else → low score.

**Plus a third factor: length.** "dog" appearing twice in a 500-page book says almost nothing. "dog" twice in a short tweet means the tweet is very much about dogs. Hence **fieldNorms**, which bias strongly toward shorter documents — terms are more concentrated there, so a short doc is more likely to be genuinely about the term.

---

## 2. Classic Lucene similarity — the fudge factors

The key insight driving the whole design: **raw TF and IDF values don't match user intuition.**

- Is an article mentioning "dog" 6 times *twice* as relevant as one mentioning it 3 times? Most users say no — more relevant, yes; twice, no.
- Is a term in 500 docs *twice* as special as one in 1000? Also no.

So Lucene damps all three inputs.

### TF → `sqrt(tf)`

| Raw TF | TF Score |
|---|---|
| 1 | 1.0 |
| 2 | 1.414 |
| 4 | 2.0 |
| 8 | 2.828 |
| 16 | 4.0 |

Result: 16 occurrences scores about twice as high as 4 — the growth rate now roughly matches intuition.

> ⚠️ **Typo in the source:** the article's table lists `1.141` for raw TF 2. `sqrt(2) = 1.414` — a digit transposition. Everything else in the table checks out.

### IDF → logarithmic

```
idf = 1 + log( numDocs / (docFreq + 1) )
```

With `numDocs = 1000`:

| Raw DF | IDF Score |
|---|---|
| 1 | 7.214 |
| 2 | 6.809 |
| 4 | 6.298 |
| 64 | 3.733 |
| 128 | 3.048 |
| 256 | 2.359 |

A term in 4 docs is about twice as special as one in 64 — again, slower growth that matches how people actually think.

> ⚠️ The article writes this inconsistently — once as `log(numDocs / docFreq + 1) + 1`, once (in the combined formula) with the `+1`s dropped entirely. The version above is what reproduces the table and what Lucene's `ClassicSimilarity` actually implements.

### Field length → `1 / sqrt(length)`

| Raw Length | Field Norm |
|---|---|
| 1 | 1.0 |
| 2 | 0.707 |
| 4 | 0.5 |
| 64 | 0.125 |
| 128 | 0.088 |
| 256 | 0.0625 |

A length-128 doc scores roughly **ten times lower** than a length-1 doc. Rationale: if you match the only term in a one-word field, that field is entirely about the term. In a 128-term field it's one of many.

### Everything combined

```
score = IDF × TF × fieldNorm
      = log(numDocs / (docFreq + 1)) × sqrt(tf) × (1 / sqrt(length))
```

**Two caveats the article flags — both are real operational gotchas:**

1. **`numDocs` is actually `maxDoc`**, which frequently includes **deleted documents**. Your IDF is computed against a document count that hasn't been reclaimed yet. This is exactly why merge state can subtly perturb scores.
2. **fieldNorms are stored as an 8-bit float** — terrible precision, and the source is blunt that it "creates all kinds of fun problems." In practice this means length distinctions get quantized into coarse buckets, so two documents of noticeably different length can share a norm.

## 3. Enter BM25

**"Best Match 25"** — released in 1994, and the 25th iteration of tweaking the relevance computation (hence the number). Roots in **probabilistic information retrieval**, which casts relevance as a probability problem: a score should reflect the probability that a user considers the result relevant.

The article deliberately skips the derivation and focuses on the shape of the curves, which is the right call for practitioners — the math looks intimidating and the behavior is intuitive.

### 3.1 BM25's IDF — almost nothing changes

Graphed, BM25's IDF looks very similar to classic Lucene IDF. The differences come from the probabilistic derivation, not from a change in intent.

**Lucene's one modification:** BM25's standard IDF can produce **negative scores** for terms with very high document frequency. Lucene adds 1 before taking the log, which makes a negative value impossible. The resulting curve tracks classic Lucene IDF closely.

**Takeaway: you don't need to rethink IDF when switching to BM25.** All the interesting change is on the TF side.

### 3.2 BM25's TF — saturation

This is the heart of it. BM25 damps term frequency **further** than TF*IDF does, and — crucially — **asymptotically**.

Ignoring length for a moment:

```
tf_score = ((k + 1) × tf) / (k + tf)
```

The curve approaches `k + 1` asymptotically (with `k = 1.2`, the usual value).

The behavioral difference stated plainly:

> **More `tf` always means more relevance, but you hit diminishing returns quickly. You never get past the asymptote — you only approach it.** Classic Lucene TF, by contrast, increases forever and never saturates.

**Tuning `k`:** most people leave it at 1.2. Changing it moves the asymptote, but the more important effect is that **a higher `k` makes TF take longer to saturate** — which stretches out the relevance difference between high-TF and low-TF documents. So:

- **Lower `k`** → saturates fast → term frequency barely differentiates documents.
- **Higher `k`** → saturates slowly → term frequency matters more across a wider range.

That's the practical framing: `k` is "how much should repetition count?"

### 3.3 Bringing document length back in

The TF section above is described as "a useful lie" — the real TF score depends on whether the document is above or below the corpus average length.

Introduce two things:

- **`L`** — this document's length relative to the corpus average, i.e. `|d| / avgDl`. `L = 2` means twice average length; `L = 0.1` means one tenth.
- **`b`** — a constant controlling how much `L` matters.

`(1.0 - b + b × L)` multiplies `k` in the denominator:

```
tf_score = ((k + 1) × tf) / (k × (1.0 - b + b × L) + tf)
```

**What the graph shows:** shorter documents hit the asymptote **much faster** — they saturate to the best possible TF score almost immediately. The reasoning is a confidence argument: short docs have few terms, so a handful of matches already makes you confident the doc is about the term. A long book needs far more matches before you can be equally confident, so it climbs slower.

**Tuning `b`:**

- `b = 0` → removes the influence of `L` entirely, collapsing back to the length-free formula.
- Higher `b` → more length influence.

A nice practical note the article makes: in classic TF*IDF you disabled norms on a field to remove length influence — a mapping-level, index-time decision. **With BM25 you just set `b = 0` on the similarity**, which is a scoring-level, reconfigurable one. Strictly better ergonomics.

### 3.4 The complete formula

```
score = IDF × ((k + 1) × tf) / (k × (1.0 - b + b × (|d| / avgDl)) + tf)
```

## 4. Comparison at a glance

| Aspect | Classic Lucene TF*IDF | BM25 |
|---|---|---|
| **TF curve** | `sqrt(tf)` — unbounded, always growing | `((k+1)·tf)/(k+tf)` — **saturating**, asymptotic |
| **IDF curve** | `1 + log(numDocs/(df+1))` | Probabilistically derived; **visually near-identical**; Lucene adds 1 inside the log to prevent negatives |
| **Length handling** | `1/sqrt(length)`, stored as an **8-bit float** | `|d|/avgDl`, relative to **corpus average**, weighted by `b` |
| **Tunability** | Effectively none without a custom similarity | **`k` and `b`** as first-class knobs |
| **Disabling length effects** | Turn off norms at the field level (index-time) | Set **`b = 0`** on the similarity (config-time) |
| **Length reference point** | Absolute field length | **Relative to corpus average** |

The last row is underrated. Classic TF*IDF penalizes length in absolute terms; BM25 asks "long *compared to what?*" — which makes it self-calibrating across corpora with wildly different document lengths.

## 5. Is BM25 right for everything?

The author is enthusiastic — he'd used it on the O'Reilly Library project for searching book chunks and found real wisdom in both term-frequency saturation and modulated length influence.

**But the caveats are the most valuable part of the article:**

- Those benefits hold for **article-length text**. Not everything we search is a blog post or a Wikipedia page.
- **The similarity should change based on what you're comparing.** Title fields have their own quirks. Hosted search services like Algolia and Swiftype built businesses partly on being very good at *short snippet* search — a different problem with different optimal scoring.
- For **numbers, images, and other entity types**, the win is not clear.

The broader argument, and the line worth remembering:

> **Relevance is never a constant — it's a user experience you're crafting.**

BM25 came out of IR competitions like TREC, where the task is well-defined document retrieval. The real world is different: you're not ranking "documents," you're ranking restaurants, products, news articles, tweets, doctors' offices. The right "similarity" for a social app might be to surface tweets from nearby friends with similar interests — **less about text similarity, more about what users need to find.**

Framing that as a rule: **BM25 is a large improvement to the core document-search problem, and a starting point rather than an answer for everything else.**

---

## 6. What to actually do with this

1. **Don't rethink IDF.** The curve barely moved. Spend your attention on TF and length.
2. **The single conceptual upgrade is saturation.** Internalize that repetition has diminishing returns with a hard ceiling. This is what stops keyword-stuffed documents from dominating.
3. **`k ≈ 1.2`, `b ≈ 0.75` are good defaults.** Change them only with evaluation data in hand, and know what each does: `k` = how much repetition counts; `b` = how much length counts.
4. **`b = 0` is the clean way to kill length normalization** on fields where length is meaningless (IDs, codes, category labels, enumerations).
5. **Length is now relative to corpus average**, so BM25 adapts to your corpus in a way classic TF*IDF didn't. This matters most for mixed-length corpora.
6. **Measure, don't assume.** The whole closing argument is that theory meeting practice is an empirical question. Set up relevance judgments before tuning.

## 7. Currency notes (2015 article, read in 2026)

The conceptual content holds up completely — this is still one of the best intuitive explanations of BM25 available. Some of the surrounding facts have moved:

- **The switch happened.** BM25 became the default in **Lucene 6 / Solr 6 (2016)** and **Elasticsearch 5.0**. The article was written in anticipation; it's now history.
- **Classic similarity is gone.** `ClassicSimilarity` (TF*IDF) was deprecated and then removed from Elasticsearch. You can no longer fall back to it as a configuration option, so the comparison here is now educational rather than a live choice.
- **`coord` and `queryNorm` were removed** along with the switch. Both were TF*IDF-era artifacts of Lucene's practical scoring function that didn't fit BM25's model. Worth knowing if you read older `explain` output.
- **Norm precision improved.** The 8-bit fieldNorm complaint was legitimate for the classic implementation; Lucene's norm handling under BM25 has since been reworked. Don't carry the old precision anxiety forward unexamined.
- **`k1` and `b` are directly configurable** in Elasticsearch via `index.similarity` settings, per-field. The article gestures at tuning; it's now a documented, first-class configuration surface.
- **The "is BM25 right for everything?" question aged extremely well.** The answer the field arrived at was *no* — which is why the modern stack is **hybrid**: BM25 as the sparse/lexical retriever, dense vector search (kNN/HNSW) as the semantic one, fused with **RRF** or a learned reranker. The article's point that entity search and short-field search need something else is exactly the gap embeddings filled.
- **BM25 remains the baseline.** Every new retrieval method is still measured against it, and it's still the sparse half of most production hybrid systems. Not superseded — complemented.
